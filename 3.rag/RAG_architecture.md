# 企业级 RAG 架构设计与技术复盘

> 本文档记录了 RAG 问答系统的核心架构选型、流式协议设计、工程化踩坑以及量化评测数据，作为项目的技术沉淀与复盘总结。

---

## 1. 核心架构选型与决策

### 1.1 分块策略：按页提取 > 按字符切分

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 按字符切分 | 整本书拼成一串，每 512 字符硬切 | 简单 | 块可能跨页，导致无法精准溯源 |
| 按页提取 | 每页单独切分，metadata 写入页码 | 页码精准，可回溯原文 | 页内仍 512 硬切，页末/下页开头语义可能断裂 |

**最终决策**：采用 **按页分块**。页码可溯源是专业 RAG 的基础，用户能回原文验证。彻底解决语义断裂需按段落/标题切，或使用滑动窗口 + 页码映射。

### 1.2 输出方式：SSE 流式 > 普通请求

- **普通请求**：需等待大模型全部生成完毕（可能长达十几秒），白屏等待体验极差。
- **SSE 流式**：打字机效果，边生成边展示，是目前主流 AI 产品的标配。
- **已知风险及处理**：流尾追加来源时，若正文末尾无空行会紧贴正文；通过后端格式化替换 + 前端补 `\n\n` 已解决。

**最终决策**：全面采用 **SSE 流式输出**。

### 1.3 向量数据入库：带元数据 > 纯文本

在 ChromaDB 中存入 `{"source": 文件名, "page": 页码}` 是刚性需求。缺乏溯源机制的 RAG 会极大降低回答的可信度。此外，带 metadata 还可支持 `where={"source": ...}` 实现多文档按来源过滤检索。

---

## 2. RAG 一句话核心总流程

> PDF 按页读取 → 分块写页码 metadata → Embedding 入 ChromaDB（cosine）→ 提问检索 Top-K → 过滤低相似度 → Rerank 精排 → 拼 Prompt → 大模型流式生成 → SSE 逐块推前端 → 打字机显示 + 文末附来源。

---

## 3. 关键技术点与底层原理

### 3.1 Embedding 原则
- Embedding 将文本映射成向量，语义相近则向量相近。维度：本地 MiniLM = 384，线上 BGE-M3 = 1024。
- **铁律**：入库和查询必须使用同一个 Embedding 模型，否则向量空间不一致，检索无效。
- 线上 API 容错：状态码非 200 返回全 0 向量可防崩溃，但会静默降质。生产环境应重试 + 抛异常 + 告警。

### 3.2 ChromaDB 核心用法
- `PersistentClient(path=...)` 数据持久化。
- 默认 L2 距离；BGE-M3 / MiniLM 都建议显式设 `metadata={"hnsw:space": "cosine"}`。
- 批量 `add` 每批约 100 条，防内存爆炸。
- `query` 返回二维列表，外层为问题数，内层为 Top-K，`results["documents"][0]` 取第一个问题的结果。

### 3.3 PDF 读取与分块
- `pypdf` 中文易乱码 → 采用 **`PyMuPDF (fitz)`**，`page.get_text("text")`，解析速度快且完美支持中文。
- 过滤策略：短块过滤（< 20 字符丢弃）；目录过滤（点号/省略号占比 > 20% 判定为目录页丢弃）。

### 3.4 检索与双阶段重排 (Rerank)
1. **向量粗排**：召回 10-20 个候选块。
2. **低相似度过滤**：`dist < 1.5` 为经验阈值，换模型需重调。
3. **Rerank 精排**：调用 BGE-Reranker 对候选块重打分，取 Top3。
- 注意：Rerank 返回的是**原始候选索引**，需用 `docs[i]` 回取；若失败则退化为取前 top_n，保证服务高可用。

## 4. 企业级 SSE 前后端契约设计（重点）

### 4.1 后端发送（生产者）
- 所有 `yield` 必须是 `data: xxx\n\n` 格式。
- **换行转义**：大模型输出的 delta 内包含的 `\n`，必须转义为 `\ndata: `。否则前端按 `\n\n` 切分时，内容会被截断或丢弃。

### 4.2 上游接收（消费者）
- 必须使用 `line.startswith("data: ")` 判断并切片截取，**绝不能用全局 `replace`**，以防误删正文里本身包含的 `data:`。
- 遇到 `[DONE]` 结束循环。
- 反代场景下 `StreamingResponse` 需加 `X-Accel-Buffering: no`。

### 4.3 前端接收（展示端）
- 严格按 `\n\n` 切分事件，只认 `data: ` 前缀。
- 使用 `marked.js` 实时渲染 Markdown，确保大模型输出的表格、代码块能正确展示。

###4.4 业务边界（闭环节点）
- 累加 full_answer，若大模型判定“无法回答”直接 return，不附带来源。

## 5. 踩坑记录与已知风险

| 坑点/风险 | 现象 | 解决方案/反思 |
|---|---|---|
| pypdf 中文乱码 | 技术书大量乱码 | 换 `PyMuPDF (fitz)`，`page.get_text("text")` |
| L2 距离排序混乱 | 相关段落距离高 | 建库显式设 `metadata={"hnsw:space": "cosine"}` |
| 异常兜底失效 | `requests.post` 超时抛异常 | `try/except` 接异常，`if not prompt` 接空结果 |
| 全 0 向量兜底 | API 报错返回全 0 向量 | 生产改重试 + 抛异常 + 告警 |
| **上游解析吞字** | 误删正文里的 `data: ` | **改用 `startswith("data: ")` 判断，切片 `[6:]` 去除前缀** |
| **无法回答却带来源** | 模型说“无法回答”却拼了来源 | 流式累加 `full_answer`，判定无法回答则直接 `return` 掐断 |
| 同步阻塞风险 | 流式生成器里阻塞 worker | 多用户换 `httpx.AsyncClient` + `async def` 异步化 |

## 6. 量化评测数据 (Hit@3)

基于 10 题评估集，统一 20 召回、统一 cosine 距离，保证对比公平。

| 检索策略 | 距离算法 | 召回数 | Hit@3 | 说明 |
|---|---|---|------:|:---|
| 本地 MiniLM | cosine | 20 | 30% | 中文理解弱，噪音多 |
| 线上 BGE-M3 | cosine | 20 | 80% | 语义理解强，大幅提升 |
| 线上 + Rerank | cosine | 20 → 3 | **90%** | 双阶段，精准剔除噪音 |

**评测备注**：
1. 样本仅 10 题，Hit@3 置信区间宽，仅作方向性对比。
2. 评测与服务召回数一致（均 20），结论可迁移至线上。
3. Rerank 多一次 API 调用，会增加几十毫秒延迟成本。

### 架构视野扩展：企业级评测体系
当前项目使用轻量级评测（Hit@3）进行快速验证。若推向企业级生产环境，需升级为**三级评测架构**：
- **检索阶段 (MTEB框架)**：引入 MRR、NDCG 等指标，需标注 Query Relevances。
- **生成阶段 (RAGAS框架)**：计算忠实度 (Faithfulness) 防幻觉，以及正确率 (Answer Correctness)。
- **方法架构**：自动指标兜底 + 大模型规模化评测 (LLM as a Judge) + 人工抽样校准。

## 7. 核心技术总结 (Key Takeaways)

1. **Embedding 原则**：入库和查询必须同模型。
2. **ChromaDB 返回**：永远二维列表，`[0]` 取第一问题。
3. **Python 拆包**：`*valid` 拆列表，`zip(*valid)` 重列。
4. **SSE 三要素**：`data: ` 前缀、`\n\n` 事件边界、`[DONE]` 结束。
5. **Rerank 双阶段**：向量粗排召回 → Reranker 精排 → 取 Top3。
6. **兜底两层**：`try/except` 接异常，`if not prompt` 接空结果。
7. **流式风险**：delta 内换行必须转 `\ndata: `，否则前端按 `\n\n` 切事件会丢内容。
